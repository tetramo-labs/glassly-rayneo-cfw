# CFW v13: relay head events before the stock re-pairing gate

V12's hook was inside `LauncherThreadMsgHandler::handleHeadUpDownEvent`, at the
call to `SysStateMonitor::notifyHeadUpDownEvent`. The stock handler checks
`LinkMonitor::isRebonding` and returns before that call. Consequently, head
messages during re-pairing could never reach the CFW relay. This is a verified
control-flow defect; the available phone log does not establish whether the
user's failed movement occurred with that flag set.

V13 hooks the dispatch call at `0x106EBCAE` instead. It relays valid launcher
message `0x1d` directions (2 up, 1 down), then calls the entire original handler
at `0x106EB4DD`. The old inner hook site is restored to stock. Re-pairing and DND
still govern stock wake behavior, but no longer gate the Glassly relay. The
sensor callbacks, UI-thread queue ownership, QUERY gate, and v12 angle control
remain intact.

## Diagnostics

DIAG appends seven bytes after v11's rendering counters (full packet offset 51):
`headEvents u32 LE`, `headDirection u8`, `headAngle u8`, `headConfig u8`.
`headEvents` counts valid messages seen after QUERY, including events dropped
when the uplink's reply reserve is full. It is not a delivery counter.

`headConfig`: 0 not requested; 1 stock apply returned; 2 no system monitor;
3 threshold preference write failed; 4 enable preference write failed.
Status 1 is not a sensor acknowledgement: the stock apply function discards
the sensor RPC result. Control 7 sends a DIAG after handling the angle request.
QUERY can read the event counter again without reopening the page.

Both SDKs log `setting head angle to …` and `received head_up/head_down …`.
These distinguish an event that never reached the phone from one received by
the phone but ignored by dashboard policy. Older DIAG replies still parse.
